# 6. High-Level `pipeignore` Implementation Specification 1.0

## 1. Purpose

`pipeignore` is the canonical batteries-included API and CLI.

It composes:

```text
pipeignore-core
pipeignore-matcher
pipeignore-filters
```

using their canonical implementations.

It MUST NOT enable `pipeignore-filters-exec` by default.

## 2. Default Construction

Conceptually:

```text
PipeIgnore()
```

MUST be equivalent to:

```text
PipeIgnore({
    matcher: canonicalMatcher,
    filters: standardFilters
})
```

## 3. Dependency Overrides

Callers SHOULD be able to override either dependency at construction.

Conceptually:

```text
PipeIgnore({
    matcher: customMatcher
})
```

uses:

```text
customMatcher
standardFilters
```

while:

```text
PipeIgnore({
    filters: customFilters
})
```

uses:

```text
canonicalMatcher
customFilters
```

If both are supplied:

```text
PipeIgnore({
    matcher: customMatcher,
    filters: customFilters
})
```

no canonical matcher or filter collection needs to participate in evaluation.

## 4. Filter Extension

The canonical API SHOULD NOT require mutation through:

```text
registerFilter()
```

The preferred mechanism is explicit collection composition:

```text
PipeIgnore({
    filters: {
        ...standardFilters,
        custom: customFilter
    }
})
```

This makes instance capabilities apparent at construction time.

## 5. Execution Filters

To enable them explicitly:

```text
PipeIgnore({
    filters: {
        ...standardFilters,
        ...executionFilters
    }
})
```

The high-level package MAY make importing these values convenient but MUST NOT
silently add them.

## 6. High-Level API

The package SHOULD expose operations conceptually equivalent to:

```text
parse(document)
compile(document)

matches(rule, path)
ignores(document, path)

filter(document, paths)
explain(document, path)
validate(document)
```

## 7. CLI

The canonical package SHOULD expose:

```text
pipeignore
```

as its primary executable.

Recommended subcommands:

```text
pipeignore check
pipeignore filter
pipeignore explain
pipeignore validate
```

### `check`

```text
pipeignore check RULEFILE PATH
```

Recommended exit semantics:

```text
0   ignored
1   not ignored
>1  error
```

Optional output MAY provide the result in human-readable or machine-readable
form.

### `filter`

```text
pipeignore filter RULEFILE [PATH...]
```

or:

```text
producer | pipeignore filter RULEFILE
```

emits only paths classified as ignored.

An inverse option SHOULD be considered:

```text
--included
```

to emit paths not ignored.

### `explain`

```text
pipeignore explain RULEFILE PATH
```

SHOULD report:

- rules evaluated;
- matcher result;
- filters evaluated;
- negation;
- winning rule;
- final classification.

It SHOULD be functionally comparable in purpose to:

```text
git check-ignore -v
```

but include PipeIgnore pipeline details.

### `validate`

```text
pipeignore validate RULEFILE
```

SHOULD detect:

- syntax errors;
- unsupported versions;
- unknown filters;
- unavailable optional capabilities;
- malformed argument syntax.

Validation SHOULD NOT require walking the filesystem unless explicitly
requested.

## 8. NUL-Safe CLI Behavior

Commands consuming or producing arbitrary paths SHOULD support a consistent
NUL-delimited option.

The same option syntax SHOULD be used across all canonical PipeIgnore CLIs where
practical.

## 9. Machine-Readable Output

`explain`, `validate`, and similar diagnostic commands SHOULD eventually support
structured output such as JSON.

The exact schema MAY remain implementation-specific until standardized
separately.
