# 2. PipeIgnore Matcher Implementation Specification 1.0

## 1. Purpose

`pipeignore-matcher` is the canonical implementation of the matcher contract
defined by PipeIgnore Matcher 1.

It provides Git-ignore-compatible matching independently of Core.

It MAY depend on an existing third-party Git-ignore matching library.

Any such dependency is an implementation detail.

Git's observable matching behavior remains the conformance authority.

## 2. Library API

The fundamental API is:

```text
match(pattern, path, context) -> boolean
```

Implementations MAY additionally expose:

```text
compile(pattern, context) -> CompiledMatcher
```

followed by:

```text
compiled.match(path, context) -> boolean
```

for efficient repeated evaluation.

## 3. Matcher Purity

The primary matching operation MUST NOT enumerate the filesystem.

Given:

```text
pattern
path
context
```

it determines whether that supplied path matches.

Filesystem traversal and candidate-path generation are outside the Matcher
contract and belong to the embedding application or to separate producer
tooling.

A root supplied through context is matching context only. It MUST NOT cause
filesystem enumeration.

## 4. Directory Information

Because Git patterns can distinguish directories, the matcher MAY require
metadata indicating whether a path is a directory.

This metadata SHOULD be supplied through context rather than discovered
unnecessarily.

## 5. Conformance

The canonical matcher SHOULD maintain differential tests against actual Git
behavior.

Where possible, test cases SHOULD compare results against:

```text
git check-ignore
```

or another authoritative Git behavior oracle.

The implementation SHOULD NOT assume that shell glob behavior is equivalent to
Git ignore behavior.

## 6. Standalone CLI

The canonical matcher SHOULD expose a command-line interface.

Recommended command name:

```text
pipeignore-matcher
```

Its purpose is **filtering**, not filesystem expansion.

The matcher pattern is supplied as a command-line argument.

Candidate paths are supplied as records through standard input.

Conceptually:

```text
producer | pipeignore-matcher PATTERN | consumer...
```

The command emits only input paths for which the matcher returns `true`.

## 7. CLI Output Contract

For each accepted path, the CLI MUST output the path representation that it
received.

The CLI MUST NOT silently normalize paths to absolute values.

## 8. NUL Mode

The CLI SHOULD support NUL-delimited input and output.

Conceptually:

```text
producer -0 |
pipeignore-matcher -0 '**/' |
consumer -0
```

This is necessary for safely supporting arbitrary Unix filenames.

## 9. Exit Status

For stream operation, exit status SHOULD represent processing success rather
than whether any input path matched.

A successful execution producing no output is therefore still a successful
execution.

## 10. No Filesystem Enumeration

The canonical Matcher CLI MUST NOT implicitly enumerate the filesystem.

Therefore:

```text
pipeignore-matcher '**/*.js'
```

does not mean "find all matching paths under the current directory".

Candidate paths MUST be supplied through standard input.

Filesystem traversal and candidate generation belong to the embedding
application or to separate producer tooling.

This keeps the Matcher abstraction consistent:

```text
pattern + candidate path + context -> boolean
```
