# 1. PipeIgnore Core Implementation Specification 1.0

## 1. Purpose

`pipeignore-core` implements the PipeIgnore language independently of any
particular matcher or filter implementation.

It is responsible for:

- parsing PipeIgnore documents;
- producing a stable intermediate representation;
- evaluating rule pipelines;
- implementing PipeIgnore rule ordering and negation semantics;
- invoking an injected matcher;
- invoking injected filters;
- producing structured diagnostics and explanations.

It MUST NOT implement Git-compatible path matching itself.

It MUST NOT provide filesystem filters itself.

It MUST NOT implicitly execute operating-system commands.

## 2. Construction

A Core instance MUST be created with:

```text
matcher
filters
```

Conceptually:

```text
Core({
    matcher,
    filters
})
```

`matcher` is REQUIRED.

`filters` is OPTIONAL and MAY be empty. If it's omitted, it equates to an empty
mapping.

A conforming implementation SHOULD reject construction without a matcher.

## 3. Matcher Interface

Core expects a matcher conforming to:

```text
match(pattern, path, context) -> boolean
```

The exact calling convention MAY be language-specific.

The matcher receives:

- the pattern;
- the path currently being evaluated;
- evaluation context.

The matcher MUST NOT determine final ignore/inclusion state. It only determines
whether the pattern portion of an individual rule matches.

## 4. Filter Interface

A filter conforms conceptually to:

```text
filter(path, arguments, context) -> boolean
```

It receives:

- the current path;
- zero or more parsed arguments;
- evaluation context.

It returns a boolean predicate result.

Filters MUST NOT be required to return the path.

Path forwarding is a CLI concern and MUST NOT be part of the in-process filter
contract.

Filters MAY be synchronous or asynchronous in language-specific implementations.

If asynchronous filters are supported, Core MUST preserve left-to-right pipeline
evaluation.

## 5. Filter Collection

Filters MUST be supplied as a mapping from filter name to filter implementation.

Conceptually:

```text
{
    "has": hasFilter,
    "has-all": hasAllFilter
}
```

Core MUST NOT require mutation-based registration.

The canonical API SHOULD favor supplying the complete collection at construction
time.

For example, conceptually:

```text
Core({
    matcher,
    filters: {
        ...standardFilters,
        ...applicationFilters
    }
})
```

A language-specific implementation MAY expose immutable helper functions for
composing filter collections.

## 6. Filter Resolution

For:

```text
**/ | has .git
```

Core resolves `has` exclusively through the supplied filter collection.

If no filter named `has` exists, Core MUST report an unknown-filter error.

Core MUST NOT:

- search the operating-system `PATH`;
- interpret the filter name as a process;
- delegate automatically to a shell.

## 7. Parsing

Core MUST parse:

```text
PATTERN
```

and:

```text
PATTERN WS "|" WS STAGE...
```

according to the PipeIgnore Core Specification.

The parser MUST preserve enough source information to identify:

- document;
- line number;
- rule;
- stage;
- filter name;
- arguments.

This information SHOULD be available to diagnostics and explanation tooling.

## 8. Intermediate Representation

Core SHOULD expose or internally maintain a representation equivalent to:

```text
Rule {
    pattern
    ruleNegated
    stages[]
    source
}
```

Each stage contains conceptually:

```text
Stage {
    filterName
    arguments[]
    negated
    source
}
```

For:

```text
projects/**/ | has package.json | ! has node_modules
```

the representation is approximately:

```text
Rule
  pattern: projects/**/
  ruleNegated: false
  source: "projects/**/ | has package.json | ! has node_modules"
  stages:
    - filter: has
      args: [package.json]
      negated: false
    - filter: has
      args: [node_modules]
      negated: true
```

For:

```text
!important/
```

the representation is approximately:

```text
Rule
  pattern: important/
  ruleNegated: true
  source: "!important/"
```

Parsed arguments MUST preserve sufficient lexical information for extensions to
distinguish escaped extension-specific syntax from its unescaped form.

Core MUST NOT eagerly consume escape sequences whose semantics belong to a
filter specification.

The representation MUST NOT depend upon a particular programming language.

## 9. Compilation

Core MAY distinguish parsing from compilation.

Conceptually:

```text
document
   ↓
parse
   ↓
AST
   ↓
compile
   ↓
compiled rules
```

Compilation MAY:

- resolve filter names;
- validate arguments where possible;
- precompile matcher patterns;
- normalize immutable metadata.

Repeated path evaluation SHOULD NOT require reparsing the document.

## 10. Individual Rule Evaluation

For each rule:

1. invoke the matcher;
2. if it returns false, the rule does not match;
3. evaluate stages from left to right;
4. apply stage negation where present;
5. reject the rule immediately when a stage resolves false;
6. return true only when every stage accepts.

Filters after a failed stage SHOULD NOT execute.

## 11. Document Evaluation

Core MUST apply inherited Git ignore ordering and negation semantics to
successfully matched rules.

Core SHOULD provide at least two conceptual levels of API:

```text
matchesRule(rule, path)
```

and:

```text
ignores(document, path)
```

The concrete names MAY differ by language.

## 12. Context

Evaluation context SHOULD provide sufficient information for matchers and
filters without requiring hidden global state.

Context MAY include:

```text
root
documentDirectory
originalPath
absolutePath
relativePath
filesystem abstraction
environment
```

Not all fields are mandatory.

Implementations SHOULD avoid forcing filters to reconstruct path context
independently.

## 13. Path Identity

Core SHOULD preserve the original supplied path.

Internal normalization MAY derive alternative representations, but:

```text
./foo
```

SHOULD remain externally observable as:

```text
./foo
```

rather than silently becoming an absolute pathname.

## 14. Errors

Core SHOULD expose structured errors for at least:

```text
SyntaxError
UnsupportedVersionError
UnknownFilterError
MatcherError
FilterError
```

Names are illustrative.

Errors SHOULD include source location where applicable.

An implementation MUST distinguish:

```text
predicate returned false
```

from:

```text
filter could not be evaluated
```

## 15. Explanation API

Core SHOULD provide structured evaluation tracing.

Conceptually:

```text
explain(document, path)
```

returns enough information to show:

```text
Rule 4
  pattern "**/"                  MATCH
  filter "has .git .hg .svn"     MATCH

Rule 8
  pattern "!important/"          MATCH

Final result: included
```

The explanation data SHOULD be structured rather than preformatted text so CLIs
and applications can render it differently.
