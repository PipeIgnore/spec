# 4. PipeIgnore Execution Filters 1.0 Specification

- **Status:** Draft
- **Version:** 1.0
- **Dependency:** PipeIgnore Core 1
- **Security classification:** Optional, security-sensitive extension

Conformance Terminology and Terminology are defined by
[PipeIgnore Core 1](1.%20core.md).

## 1. Introduction

PipeIgnore Execution Filters defines filters that delegate path evaluation to
external programs.

Support for this specification is OPTIONAL.

A PipeIgnore Core implementation MUST NOT be considered non-conforming merely
because it does not implement Execution Filters.

Applications processing untrusted PipeIgnore documents SHOULD disable these
filters.

This specification defines:

```text
exec
shell
```

Neither filter has special syntax in PipeIgnore Core.

## 2. Security Model

Execution Filters cross the boundary between declarative path matching and
arbitrary process execution.

Implementations MUST NOT enable Execution Filters merely as an implicit fallback
for unknown filter names.

Thus:

```text
**/ | grep something
```

MUST NOT mean:

```text
execute grep
```

unless `grep` has explicitly been registered as a filter by the embedding
implementation.

External execution requires an explicit Execution Filter:

```text
**/ | exec grep ...
```

or:

```text
**/ | shell ...
```

## 3. `exec`

Syntax:

```text
exec PROGRAM [ARGUMENT ...]
```

`exec` executes `PROGRAM` directly without invoking a command shell.

The implementation MUST preserve argument boundaries.

Shell metacharacters MUST NOT receive shell semantics.

For example:

```text
exec program "*" "$HOME" ">"
```

MUST NOT implicitly perform glob expansion, environment-variable expansion or
redirection.

### 3.1 Current Path Placeholder

PipeIgnore Execution Filters 1 defines:

```text
{}
```

as the current path placeholder.

The placeholder MAY occur zero or more times within arguments supplied to
`exec`.

Every occurrence of `{}` within an argument value MUST be replaced with the
current path before process execution.

The sequence `{}` is treated as a single PipeIgnore placeholder token for
substitution purposes.

The sequence `\{}` escapes that placeholder token as a whole and produces the
literal characters `{}`.

Neither `{` nor `}` has special meaning independently.

Substitution MUST occur structurally within the argument value and MUST NOT
cause shell parsing, word splitting, pathname expansion, or any other command
interpreter behavior.

For example:

```text
**/ | exec test -e {}/.git
```

evaluated for:

```text
/path/My Project
```

conceptually executes the equivalent of:

```text
argv[0] = "test"
argv[1] = "-e"
argv[2] = "/path/My Project/.git"
```

The resulting pathname remains one argument regardless of whitespace or shell
metacharacters contained in the path.

The placeholder represents the externally visible/original form of the current
path unless the implementation explicitly documents another representation.

Use of `{}` is explicit and OPTIONAL. PipeIgnore MUST NOT implicitly append or
inject the current path when no `{}` placeholder is present.

Future versions MAY define additional path representations or placeholders.

### 3.2 Result

An executed program returning a successful process status MUST cause `exec` to
accept the current path.

A non-successful process status MUST cause `exec` to reject the current path.

On POSIX systems, exit status `0` MUST represent acceptance.

Non-zero exit status MUST represent rejection unless process execution itself
failed.

Failure to start the requested program SHOULD be reported as an execution error
rather than silently interpreted as ordinary rejection.

## 4. `shell`

Syntax:

```text
shell COMMAND [ARGUMENT ...]
```

`shell` executes `COMMAND` using a command interpreter.

`COMMAND` is the first argument to the `shell` filter and contains the command
or script to be evaluated by that interpreter.

Any following arguments are passed to the invoked command interpreter as
positional arguments.

Before invocation, every occurrence of the PipeIgnore `{}` placeholder within
those positional argument values MUST be replaced with the current path using
the same structural substitution rules defined for `exec`.

PipeIgnore MUST NOT perform `{}` substitution inside `COMMAND` itself.

For example:

```text
**/ | shell 'test -e "$1/.git"' {}
```

passes the current path as the first positional argument.

The following is equivalent in intent:

```text
**/ | shell 'test -e "$1"' {}/.git
```

but passes the current path with `/.git` already appended as the first
positional argument.

Use of `{}` is OPTIONAL. A `shell` filter invocation MAY contain no current-path
placeholder at all.

PipeIgnore MUST NOT infer from the contents of `COMMAND` that a positional
argument was intended or omitted.

Unlike `exec`, `shell` intentionally permits the command interpreter to apply
its normal semantics, potentially including:

- variable expansion;
- shell pipelines;
- redirection;
- command substitution;
- shell globbing;
- compound commands.

The exact command interpreter is implementation-defined and MUST be documented.

### 4.1 POSIX Shell Invocation

When the selected interpreter follows POSIX `sh -c` positional-argument
semantics, the canonical conceptual invocation is:

```text
sh -c COMMAND pipeignore ARG1 ARG2 ...
```

Accordingly:

```text
$0 = pipeignore
$1 = ARG1
$2 = ARG2
...
```

The value `pipeignore` provides a stable and descriptive `$0` value and is not
an additional PipeIgnore argument.

PipeIgnore assigns no special meaning to `$1`, `$2`, or other positional
parameter syntax. They are ordinary features of the selected command
interpreter.

Non-POSIX implementations SHOULD provide equivalent positional-argument
semantics where practical and MUST document any differences.

## 5. Shell Command Boundaries

`COMMAND` MUST be parsed as one PipeIgnore argument before it is passed to the
command interpreter.

PipeIgnore quoting therefore determines the boundary of `COMMAND`, while the
contents of `COMMAND` are subsequently interpreted by the selected shell.

For example:

```text
**/ | shell 'test -e "$1/.git"' {}
```

contains a PipeIgnore pipeline with one `shell` stage.

A shell pipeline may safely occur inside the quoted command:

```text
**/ | shell 'test -e "$1" | grep -q something' {}
```

The `|` characters inside the quoted argument belong to the shell command and
MUST NOT be interpreted as PipeIgnore pipeline operators.

## 6. Result of `shell`

Successful shell execution MUST accept the current path.

Unsuccessful shell execution MUST reject it.

Execution errors SHOULD be distinguishable from an ordinary false predicate.

## 7. Negation

Execution Filters use ordinary PipeIgnore Core negation.

For example:

```text
**/ | ! exec test -e {}/.git
```

means that the stage accepts when the external `test` predicate rejects.

Likewise:

```text
**/ | ! shell 'test -e "$1/.git"' {}
```

uses Core negation.

Execution Filters MUST NOT define a separate negation mechanism.

## 8. Relationship to Standard Filters

Where a Standard Filter exists, applications SHOULD generally prefer it over an
equivalent Execution Filter.

For example:

```text
**/ | has .git
```

is preferable to:

```text
**/ | exec test -e {}/.git
```

when the Standard Filters extension is available.

The two expressions are not required to be universally equivalent because the
Standard Filter has precisely specified PipeIgnore semantics, while the external
program's behavior depends upon the operating environment.

## 9. Disabling Execution Filters

Applications MAY disable:

```text
exec
```

and/or:

```text
shell
```

independently.

For example, an application MAY permit:

```text
exec
```

while prohibiting:

```text
shell
```

to avoid shell interpretation.

Applications SHOULD provide a means to determine whether Execution Filters are
enabled.

A security-sensitive implementation MAY omit this specification entirely.

## 10. Standalone Commands

Unlike Standard Filters, `exec` and `shell` need not be exposed as standalone
PipeIgnore utilities because their primary purpose is adapting external
execution into the PipeIgnore filter contract.

Implementations MAY nevertheless expose them independently.

## 11. Security Considerations

A PipeIgnore document containing Execution Filters MUST be treated as executable
input.

Applications MUST NOT evaluate untrusted:

```text
exec
```

or:

```text
shell
```

stages without an appropriate security policy.

`shell` presents substantially greater injection risk because command strings
are interpreted by a shell.

`exec` SHOULD be preferred whenever shell features are unnecessary.

Implementations SHOULD avoid constructing shell command strings when evaluating
`exec`.

Environment inheritance, working directory, resource limits, timeouts and
process privileges are implementation-defined and SHOULD be configurable by
security-sensitive applications.
