# 1. PipeIgnore Core 1.0 Specification

- **Status:** Draft
- **Version:** 1.0
- **Date:** 2026-08-18

## 1. Introduction

PipeIgnore is a line-oriented path filtering language derived from the Git
ignore pattern syntax.

PipeIgnore extends a Git ignore rule by allowing its path matcher to be followed
by an ordered pipeline of filters.

A traditional Git ignore rule:

```text
*.log
```

is also a valid PipeIgnore rule.

PipeIgnore additionally permits expressions such as:

```text
**/ | has .git .hg .svn
```

The path matcher determines whether the current path is a candidate for the
rule. Each subsequent filter further constrains that match.

PipeIgnore Core defines:

- the structure of PipeIgnore documents;
- compatibility with Git ignore patterns;
- pipeline syntax;
- filter invocation;
- filter negation;
- filter composition;
- rule evaluation;
- extension and error-handling requirements.

PipeIgnore Core deliberately does **not** define any filters.

The matching of the initial Git-compatible pattern is defined separately by the
**PipeIgnore Matcher Specification**.

Standard filesystem filters are defined separately by the **PipeIgnore Standard
Filters Specification**.

Filters capable of executing external processes are defined separately by the
**PipeIgnore Execution Filters Specification**.

## 2. Conformance Terminology

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**,
**RECOMMENDED**, **MAY**, and **OPTIONAL** are to be interpreted as described by
RFC 2119 and RFC 8174 when they appear in all capitals.

An implementation conforms to PipeIgnore Core 1.0 if it implements all REQUIRED
behavior defined by this specification.

Conformance with PipeIgnore Core does not imply implementation of any particular
filter library.

## 3. Terminology

**Path** A filesystem path being evaluated.

**Pattern** The Git-compatible path-matching portion of a PipeIgnore rule.

**Matcher** The operation that evaluates a pattern against a path.

**Filter** A named predicate receiving the current path and zero or more
arguments and returning an accept or reject result.

**Stage** One filter invocation, optionally negated.

**Pipeline** A pattern matcher followed by zero or more filter stages.

**Rule** One complete PipeIgnore expression.

**Document** A sequence of PipeIgnore rules, comments and blank lines.

## 4. Relationship to Git Ignore

Unless explicitly modified by this specification, the pattern portion of a
PipeIgnore rule MUST follow Git ignore syntax and semantics as defined by
`gitignore(5)`.

[Git gitignore documentation](https://git-scm.com/docs/gitignore)

This includes the semantics of:

- comments;
- blank lines;
- `!` rule negation;
- `/`;
- `*`;
- `?`;
- character ranges;
- `**`;
- directory-only patterns;
- escaping;
- rule ordering;
- rule precedence.

A rule containing no PipeIgnore pipeline MUST have the same meaning as the
corresponding Git ignore rule.

PipeIgnore extends the **matcher of a rule**. It does not redefine the Git
ignore rule-selection and precedence model.

Core MUST recognize and remove an unescaped leading Git rule-negation marker `!`
before passing the pattern portion to the matcher.

An escaped leading `\!` MUST retain the meaning assigned to it by Git ignore
syntax and MUST NOT be interpreted by Core as rule negation.

The negation state MUST be retained as part of the rule metadata and applied
only when determining the rule's final include/exclude effect.

The matcher therefore receives the underlying pattern without the leading
rule-negation marker.

```text
!important/
```

is conceptually equivalent to:

```text
ruleNegated = true
pattern = "important/"
```

and Core invokes the matcher with the underlying pattern:

```text
match("important/", path, context)
```

not:

```text
match("!important/", path, context)
```

## 5. Document Identification

A PipeIgnore document MAY contain:

```text
# syntax: pipeignore
```

An implementation MUST interpret this as PipeIgnore version 1 unless another
version is explicitly specified.

The equivalent explicit form is:

```text
# syntax: pipeignore/1
```

The modeline is OPTIONAL when the consuming application already knows that the
document uses PipeIgnore syntax.

Future specifications MAY assign meaning to other version numbers.

A PipeIgnore implementation MUST NOT interpret an unsupported explicitly
specified version as version 1.

## 6. Whitespace

For the purposes of PipeIgnore syntax:

```text
WS = 1*(SP / HTAB)
```

That is, `WS` consists of one or more ASCII spaces or horizontal tabs.

Where this specification requires `WS`, any positive number of spaces and/or
horizontal tabs MUST be accepted.

For example, these are equivalent:

```text
**/ | has .git
**/    |    has .git
```

The canonical presentation SHOULD use a single ASCII space around operators and
between ordinary tokens:

```text
**/ | has .git
```

Additional whitespace MAY be used for alignment.

## 7. Pipeline Syntax

An extended PipeIgnore rule has the conceptual grammar:

```text
RULE          = PATTERN *(PIPE STAGE)
PIPE          = WS "|" WS
STAGE         = [NEGATION] FILTER *(WS ARG)
NEGATION      = "!" WS
FILTER        = NAME
ARG           = BARE / QUOTED
NAME          = 1*(ALPHA / DIGIT / "_" / "-")
QUOTED        = SINGLE_QUOTED / DOUBLE_QUOTED
```

`FILTER` identifies a filter by name. Filter names are case-sensitive.

`ARG` represents one argument value after PipeIgnore quoting and escaping have
been processed.

`BARE`, `SINGLE_QUOTED`, and `DOUBLE_QUOTED` are lexical argument forms whose
recognition is governed by the quoting, token-boundary, and escaping rules of
Section 12.

Their complete lexical structure is deliberately not expressed in the conceptual
grammar above because escaping is context-sensitive and extensions MAY define
additional escaped syntax within argument values.

The exact lexical recognition of escaped syntax is defined by Section 12 rather
than entirely by the grammar above, because escaping is context-sensitive.

Whitespace and pipeline operators occurring within quoted arguments MUST NOT
terminate the argument or stage.

`PATTERN`, `FILTER`, and `ARG` are subject to the lexical rules defined
elsewhere in this specification and by the inherited Git ignore syntax.

The pipeline operator is therefore recognized only when `|` is surrounded on
both sides by `WS`.

Consequently:

```text
foo | has bar
```

contains a pipeline.

However:

```text
foo|bar
```

does not.

The latter is part of the Git-compatible pattern.

## 8. Filter Invocation

A filter stage consists of:

```text
FILTER [ARGUMENT ...]
```

The current path is implicit.

For example:

```text
**/ | has .git .hg .svn
```

conceptually invokes:

```text
has(current-path, ".git", ".hg", ".svn")
```

A filter MUST return a logical result equivalent to:

```text
accept
```

or:

```text
reject
```

Core does not prescribe whether a filter is implemented:

- internally;
- as a library function;
- as an external executable;
- through a plugin system;
- by another mechanism.

Those implementation details MUST NOT change the filter's defined observable
semantics.

## 9. Filter Resolution

An implementation MUST have a mechanism for resolving filter names.

PipeIgnore Core does not prescribe that mechanism.

An implementation MAY provide:

- built-in filters;
- dynamically registered filters;
- plugin filters;
- application-specific filters;
- filters defined by another PipeIgnore specification.

An unknown filter MUST NOT automatically be interpreted as an operating-system
command.

Implementations SHOULD report an unknown filter as an error.

## 10. Pipeline Evaluation

Given:

```text
PATTERN | FILTER-A args | FILTER-B args
```

and path `P`, evaluation is conceptually:

```text
match(PATTERN, P)
AND FILTER-A(P, args)
AND FILTER-B(P, args)
```

Evaluation MUST proceed from left to right.

If the pattern rejects the path, the rule does not match and no filter need be
evaluated.

If a filter rejects the path, the rule does not match and subsequent filters
SHOULD NOT be evaluated.

The rule matches only when:

1. its pattern matches; and
2. every non-negated filter accepts; and
3. every negated filter rejects before negation.

Pipeline composition in PipeIgnore 1 therefore represents logical conjunction.

## 11. Filter Negation

A filter stage MAY be negated using:

```text
! WS
```

For example:

```text
**/ | ! has .git
```

The negation operator inverts the logical result of that filter invocation.

Conceptually:

```text
! FILTER(P, args)
```

means:

```text
NOT FILTER(P, args)
```

The following is valid:

```text
**/ | !     has .git
```

because `WS` permits multiple spaces or tabs.

The following is not filter-negation syntax:

```text
**/ | !has .git
```

PipeIgnore 1 requires whitespace between `!` and the filter name.

Filter negation is distinct from Git ignore rule negation.

At the beginning of a pattern:

```text
!important/
```

has the inherited Git ignore meaning.

After a pipeline operator:

```text
**/ | ! has important
```

negates a filter.

## 12. Arguments

Arguments are separated by `WS`.

An argument MAY be unquoted or quoted using either single (`'`) or double (`"`)
quotation marks.

Single-quoted and double-quoted arguments have identical semantics. The choice
of delimiter exists only to allow the other quotation character to occur without
escaping.

For example:

```text
"it's valid"
'he said "hello"'
```

each represents a single argument.

Quotation marks used to delimit an argument are not part of the resulting
argument value.

Quoted arguments MAY contain whitespace and PipeIgnore syntax characters without
those characters being interpreted as separators or operators.

For example:

```text
shell 'printf "%s\n" "$1"'
```

contains one argument following the `shell` filter name.

PipeIgnore quoting is a tokenization mechanism only. It MUST NOT perform:

- environment-variable expansion;
- command substitution;
- pathname or glob expansion;
- redirection;
- shell pipeline evaluation.

A pipeline operator MUST be recognized only outside quoted arguments.

Implementations MUST provide escaping for a quotation delimiter when that
delimiter must occur within an argument delimited by the same quotation
character.

Quoting controls token boundaries. Escaping controls literal interpretation.

The escaping mechanism MUST NOT introduce general shell evaluation.

### 12.1 Quoting

Single (`'`) and double (`"`) quotation marks are equivalent argument
delimiters.

Their primary purpose is to preserve whitespace within a single argument and to
allow either quotation character to appear without escaping when the other is
used as the delimiter.

For example:

```text
"it's valid"
'he said "hello"'
```

Quotation delimiters are removed during parsing and are not part of the
resulting argument.

Quotation does not disable PipeIgnore-specific semantics that apply to the
resulting argument value unless explicitly stated by the specification defining
that syntax.

### 12.2 Escaping

PipeIgnore uses selective escaping.

A backslash has escape semantics only when it precedes a character or sequence
that would otherwise have syntactic meaning in the current PipeIgnore context.

A backslash preceding an ordinary character MUST be preserved literally.

For example:

```text
C:\Users\example
```

represents the literal value:

```text
C:\Users\example
```

and does not interpret `\U` or `\e` as escape sequences.

Quotation delimiters MAY be escaped when they would otherwise terminate the
current quoted argument.

A backslash MAY also be used to prevent recognition of a PipeIgnore pipeline
operator when `|` would otherwise satisfy the `PIPE` grammar.

PipeIgnore Core does not assign intrinsic meaning to `{}`.

Specifications defining filter-specific syntax MAY define additional escape
sequences within argument values.

Core MUST preserve sufficient information for such filter-specific escaping to
be interpreted by the filter specification that defines it.

In particular, when an extension defines `\{}` as an escaped form of `{}`, Core
MUST NOT make the escaped and unescaped forms indistinguishable before that
extension processes the argument.

Individual `{` and `}` characters have no special meaning and do not require
escaping.

Likewise, `|` has no special meaning unless it satisfies the PipeIgnore pipeline
operator grammar:

```text
PIPE = WS "|" WS
```

Therefore:

```text
foo|bar
foo |bar
foo| bar
```

contain literal `|` characters, while:

```text
foo | bar
```

contains a PipeIgnore pipeline operator when occurring outside a quoted
argument.

## 13. Path Semantics

The externally visible representation of a path SHOULD be preserved throughout a
pipeline.

An implementation MAY internally maintain:

```text
original path
absolute path
root-relative path
```

or equivalent representations.

Internal normalization MUST NOT unnecessarily alter externally observable paths.

Implementations MUST NOT resolve symbolic links unless required by a filter's
semantics or explicitly requested by the embedding application.

## 14. Rule Ordering

Once the complete pipeline has been evaluated, the resulting match participates
in ordinary Git ignore rule ordering and precedence.

Thus:

```text
**/ | has .git
!important-project/
```

does not introduce a new precedence model.

The first rule merely has a more expressive matching predicate than an ordinary
Git ignore pattern.

## 15. Errors

Implementations SHOULD report:

- malformed pipeline operators;
- malformed stages;
- unknown filters;
- invalid arguments when detectable;
- unsupported language versions.

An implementation MUST NOT silently execute an unknown filter as an external
command.

Security-sensitive applications SHOULD fail closed or fail fast when invalid
rules could result in unintended inclusion of data.

## 16. Extensibility

PipeIgnore Core 1 deliberately does not define:

- standard filters;
- general boolean expressions;
- parenthesized expressions;
- nested pipelines;
- explicit pipeline-level OR;
- transformations;
- variables;
- command substitution;
- implicit command execution.

Future versions MAY define such facilities.

## 17. Example

```text
# syntax: pipeignore

*.tmp
*.log

**/ | has .git .hg .svn
projects/**/ | has package.json | ! has node_modules
```

The names `has` and `node_modules` have no intrinsic meaning to PipeIgnore Core.
Their behavior depends on the registered filters.
