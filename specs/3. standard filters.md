# 3. PipeIgnore Standard Filters 1.0 Specification

- **Status:** Draft
- **Version:** 1.0
- **Dependency:** PipeIgnore Core 1

Conformance Terminology and Terminology are defined by
[PipeIgnore Core 1](1.%20core.md).

## 1. Introduction

PipeIgnore Standard Filters defines a portable vocabulary of filesystem
predicates suitable for use as PipeIgnore filter stages.

Support for this specification is OPTIONAL for a PipeIgnore Core implementation.

A conforming Standard Filters implementation MUST implement the filters
designated REQUIRED by this specification.

PipeIgnore Core itself assigns no special syntactic status to these names.

Thus:

```text
| has .git
```

is syntactically an ordinary filter invocation.

Its semantics come from this specification.

## 2. Common Semantics

Each Standard Filter receives:

```text
current path
arguments...
```

and returns:

```text
accept
```

or:

```text
reject
```

Filters MUST NOT transform the externally visible path.

A standalone implementation MAY expose the same filters as command-line
programs.

Whether a filter executes in-process or through an external executable MUST NOT
alter its defined matching semantics.

## 3. `has`

**Status:** REQUIRED

Syntax:

```text
has NAME [NAME ...]
```

`has` accepts the current path if:

1. the current path represents a directory; and
2. that directory contains an immediate entry matching at least one supplied
   `NAME`.

`NAME` is a literal string representing a filesystem entry name. Future spec
revisions or specialized filters MAY introduce gitignore pattern matching
semantics with filesystem walk semantics.

Multiple arguments use OR semantics.

Therefore:

```text
has .git .hg .svn
```

means conceptually:

```text
has .git
OR has .hg
OR has .svn
```

The matching child MAY be of any filesystem type.

In particular:

```text
has .git
```

MUST accept both a directory containing a `.git` directory and one containing a
`.git` regular file.

`has` examines immediate children only unless a future specification explicitly
introduces recursive semantics.

An error reading the current path or its children MUST be treated as an error,
not a rejection.

## 4. `has-all`

**Status:** REQUIRED

Syntax:

```text
has-all NAME [NAME ...]
```

`has-all` accepts the current path if:

1. the current path represents a directory; and
2. every supplied `NAME` exists as an immediate child.

`NAME` is a literal string representing a filesystem entry name. Future spec
revisions or specialized filters MAY introduce gitignore pattern matching
semantics with filesystem walk semantics.

Arguments use AND semantics.

Thus:

```text
has-all package.json package-lock.json
```

requires both entries.

An error reading the current path or its children MUST be treated as an error,
not a rejection.

## 5. Relationship Between `has` and `has-all`

`has` and `has-all` require at least one argument. Invocation with zero
arguments MUST be treated as an invalid filter invocation, not as a false
predicate.

For one argument:

```text
has foo
```

and:

```text
has-all foo
```

are logically equivalent.

For multiple arguments:

```text
has foo bar
```

means:

```text
foo OR bar
```

while:

```text
has-all foo bar
```

means:

```text
foo AND bar
```

PipeIgnore Core negation can be applied normally:

```text
**/ | ! has .git
```

or:

```text
**/ | ! has-all foo bar
```

No filter-specific negation syntax is defined.

## 6. Additional Standard Filters

Future revisions MAY define additional filesystem predicates, including
predicates concerning:

- filesystem object type;
- size;
- modification time;
- ownership;
- permissions.

PipeIgnore Standard Filters 1.0 deliberately does not standardize such filters
until their syntax, portability and comparison semantics are established.

Names such as:

```text
type
size
mtime
```

are therefore not standardized by version 1.0.

Implementations MAY provide them as extensions.

## 7. Standalone Commands

An implementation MAY expose:

```text
has
has-all
```

as standalone commands.

The canonical PipeIgnore implementation is RECOMMENDED to expose Standard
Filters both:

- as in-process filters usable by PipeIgnore Core;
- as independent command-line utilities.

This is an implementation recommendation, not a requirement of the language.

A command-line implementation SHOULD support stream filtering:

```text
producer | has .git .hg .svn
```

and SHOULD provide a NUL-delimited mode.

## 8. Example

```text
# syntax: pipeignore

**/ | has .git .hg .svn
**/ | has package.json | ! has node_modules
**/ | has-all package.json package-lock.json
```
