# 2. PipeIgnore Matcher 1.0 Specification

- **Status:** Draft
- **Version:** 1.0
- **Dependency:** Git ignore pattern semantics

Conformance Terminology and Terminology are defined by
[PipeIgnore Core 1](1.%20core.md).

## 1. Introduction

PipeIgnore Matcher defines the mandatory path matcher used as the initial stage
of every PipeIgnore rule.

It implements the pattern semantics required by Git ignore rules.

A PipeIgnore Core 1 implementation MUST provide, or depend upon, an
implementation conforming to PipeIgnore Matcher 1.

## 2. Abstract Interface

The fundamental operation is:

```text
match(pattern, path, context) -> boolean
```

where:

- `pattern` is a Git ignore-compatible pattern;
- `path` is the path being evaluated;
- `context` contains any root or directory information required by Git ignore
  semantics.

The matcher MUST NOT require filesystem enumeration to evaluate an already
supplied path.

## 3. Git Compatibility

PipeIgnore Matcher 1 MUST implement the applicable pattern semantics documented
by Git in `gitignore(5)`.

[Git gitignore documentation](https://git-scm.com/docs/gitignore)

A conforming implementation SHOULD reproduce actual Git behavior in edge cases
where a naive shell glob implementation would differ.

The matcher MUST support the semantics of at least:

```text
*
?
[...]
**
/
trailing /
escaped metacharacters
```

as required by Git ignore patterns.

## 4. Relative Matching

Matching MUST be performed relative to the appropriate ignore root or document
location according to Git semantics.

Given:

```text
root     = /home/user/project
path     = /home/user/project/src/main.js
```

the matcher MAY internally evaluate:

```text
src/main.js
```

while preserving the caller's original representation externally.

## 5. Directory Information

Git ignore syntax distinguishes some directory patterns from file patterns.

The matcher MAY therefore receive filesystem metadata or an indication that the
supplied path represents a directory.

The exact API is implementation-defined.

## 6. Relationship to PipeIgnore Core

For:

```text
**/ | has .git
```

PipeIgnore Matcher evaluates only:

```text
**/
```

against the current path.

It MUST NOT interpret:

```text
| has .git
```

as part of the matcher pattern.

Separating Core parsing from Matcher matching is REQUIRED.

## 7. Standalone Command

An implementation MAY expose PipeIgnore Matcher as a standalone command.

The canonical implementation is RECOMMENDED to do so.

A standalone Matcher acts as a predicate over candidate paths. It does not
enumerate the filesystem.

The matcher pattern is supplied as a command-line argument.

Candidate paths are supplied as records through standard input.

For stream-oriented use:

```text
producer | matcher PATTERN | consumer
```

the Matcher emits only candidate path records that match PATTERN.

The original representation of an accepted path record MUST be preserved.

Filesystem enumeration and candidate-path generation are outside the scope of
PipeIgnore Matcher.

## 8. Versioning

PipeIgnore Matcher is independently versioned.

A PipeIgnore Core 1 implementation requires a matcher conforming to the
PipeIgnore Matcher 1 interface and semantics. It does not require the canonical
pipeignore-matcher implementation.

The PipeIgnore document modeline does not independently select a Matcher version
in PipeIgnore 1.
